Workflow architecture

The handoff is where a workflow earns its keep

A timeout, a duplicate record and an uncertain state are better architecture questions than a shiny integration diagram.

CTDG Engineering team26 November 20267 min read

Start with the thing that must arrive

When a customer makes an enquiry, the objective is not to move a message between two applications. It is to get the correct information to the appropriate person, with an accurate understanding of what happened. An integration that moves incomplete information faster has not necessarily made the business better. Start with the outcome, the point at which it is confirmed and the person or system that owns the next decision.

What a timeout really means

Imagine a service accepts a request but the connection drops before the caller receives confirmation. We cannot infer that the request failed. The receiving system may have written the record. Retrying with a fresh identifier could create a duplicate. Where the integration supports it, a stable request key and a lookup against the authoritative record can make a retry safer. An identifier is not magical duplicate protection unless the receiving system actually honours it.

Separate an interface from a working system

A public demo can show a useful journey without proving that every production system is integrated. Our Interactive Demos portfolio makes this distinction explicit: selected public HTML provides interface evidence; the live experience is separate. Axiom Architect's documented workflow describes intake, diagnosis and an implementation blueprint rather than promising that every step is operational in every environment.

The missing response is not a missing record

Consider a fictional enquiry with identifier SIM-104. The sender creates a request and waits. The receiving system writes the record but the connection drops before the response comes back. The sender now knows that the request was attempted, not whether it succeeded. The receiving system knows a record exists, but the sender has not obtained that evidence. This disagreement between what happened and what the caller can establish is the interesting part of the problem.

It is tempting to add a retry button and move on. But if pressing that button generates a completely new request identifier, the receiver may treat the second request as a new customer enquiry. The second request can return a perfectly valid success response. At that point the sender has a green tick and the business has two records. The integration appears healthy precisely when it has created extra work. The problem is not that a retry exists; it is that the retry has no agreed relationship to the original request.

The contract behind a safe retry

Idempotency means that repeating an operation under a defined contract does not produce additional unintended effects. A stable request key can support that contract when the receiving service recognises it, associates it with the original operation and handles repeated submissions consistently. Merely sending a header called an idempotency key does not establish that guarantee. The receiving system must implement and document the behaviour.

A practical design also needs to consider what happens if the same key is used with different contents, how long the key remains meaningful and whether an accepted request can still be processing when a lookup is made. In the simplified browser simulator we assume an authoritative lookup, a stable key honoured by the service and a successful bounded retry when the record is absent. Those assumptions are deliberately visible. A real integration needs its own tests against the receiving contract before an engineer can rely on the same behaviour.

The four situations worth testing first

In the normal case a confirmation arrives with a matching record reference, so there is no reason to retry. In the second case the record has been created but the response is lost. A lookup using the original key establishes its existence and avoids a new write. In the third case the first write never creates the record; a reliable lookup can establish absence, after which a bounded retry can proceed under the agreed contract. In the fourth case the lookup itself is unavailable. There is no reliable basis for claiming either success or absence, so the guarded path stops and hands off an unresolved state.

The simulator runs the guarded path and a blind-retry comparison together. The same initial conditions go into both paths. The resulting counts show the difference between write attempts, records actually created in the fictional model and records confirmed to the caller. That last distinction is important: the model can reveal ground truth for educational purposes, whereas a real sender cannot simply inspect an invisible database after a timeout. It must obtain evidence from an authorised system.

What the next person needs to know

A handoff is not a dump of every log line. It is a compact account of the operation, its current evidence, what remains unknown, any previous attempts and the next decision. For an unresolved enquiry, that could be the original correlation key, the last observed response and the fact that the verification service is unavailable. It should make clear that no new request has been authorised and that a responsible person needs to inspect the original record before deciding what to do.

A good handoff also avoids the opposite failure: creating an exception queue that nobody owns. The business needs to agree who can investigate, when escalation is appropriate and what evidence is needed to close the exception. Technical retry limits without an accountable owner simply move the unresolved work into another system. The aim is to reduce manual work while preserving a way to recover when automation reaches the limits of its evidence.

Testing the uncomfortable paths

A useful integration test suite should include an ordinary success, a timeout before a write, a timeout after a write and unavailable verification. It should check that repeated submissions using the same request identity do not create unexpected records under the stated service contract. A negative test should demonstrate what happens when a different identity is used. The engineering team should inspect both the returned response and the resulting state rather than assuming that an HTTP success alone establishes the full business outcome.

For production, further questions arise around concurrent requests, delayed processing, permission changes, expiry of deduplication records and recovery after a restart. These are proposed acceptance cases, not a claim that every CTDG integration currently passes them. The public Workbench tests the deliberately small deterministic model. A customer implementation requires a separate, bounded verification exercise with its own service contract and acceptance criteria. This distinction keeps a useful educational example from turning into an unsupported reliability guarantee.

How the same principle applies beyond enquiries

The June Axiom Architect history records work on proposal payment synchronisation, verification and hardening. We can inspect those commits as historical engineering checkpoints. A payment interface is a particularly good reminder that a successful screen action and a confirmed downstream business state are different things. We do not infer a successful live transaction from the presence of an audit or a source file. The source history tells us what was developed; actual payment evidence is a separate matter.

Similar questions apply to bookings, onboarding, document delivery and support tickets. Which system is authoritative? What identifies the same operation? What confirms completion? What happens if the response is missing? Who owns an exception? Asking those questions before buying another integration tool often gives a better starting point than drawing a larger diagram. The diagram becomes useful when each arrow has a defined responsibility, a record of what crossed it and a way to handle an unsuccessful handoff.

A useful automation discussion

Before we propose an automation, we want to understand what the existing business does when something goes wrong. The apparently small exceptions often reveal the real requirements: people reconcile duplicate records, check a payment manually or contact somebody because a confirmation never arrived. Making that work visible is a better starting point than promising to replace it with an assistant.

The simulator is an invitation to try this thinking without touching a live service. Select a fault and watch the two policies respond automatically. Then ask which parts of the model would need to change for your own business. That is the beginning of a useful technical conversation, not a claim that a browser demonstration is a complete production integration.

Make recovery visible

When retries cannot establish an outcome, stop and surface the uncertainty. Give the responsible person enough context to decide what happens next. Our Workbench includes a fictional enquiry with an ambiguous integration response. It illustrates a wider engineering principle: make failures legible instead of hiding them behind another green status icon.
